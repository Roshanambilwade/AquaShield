## Purpose, architecture and acceptance boundaries

AquaShield connects household shortage evidence to explainable municipal assessment, human-approved resource response, owned operator trips and recorded delivery. React/Vite and Express remain JavaScript npm workspaces; MongoDB/Mongoose persist state. Modular backend services own clustering, confidence, severity, population estimates, fairness, quantity constraints, distance/ETA and numerical prediction. Strands with explicit GoogleModel/Gemini explains bounded evidence; no model approves or assigns resources.

The traceability document covers sections 1–80 and the twelve overrides, including field/model/API differences rather than treating a phase name as acceptance. MATCH means supported local behavior was exercised; PARTIAL identifies unmet broader requirements; MISSING means no corresponding implementation; CONFLICT identifies an approved architectural equivalent; NOT VERIFIED identifies external or unexecuted evidence; INTENTIONALLY DEFERRED identifies excluded work. These categories do not establish production readiness or physical outcomes.

## Confirmed delivery-verification issue and minimal correction

The user identified **ADMIN — Trips and deliveries**, not an operator trip state. `DeliveriesPage` renders `TripCard` with `admin`; operator controls are intentionally under `!admin`. The owning OPERATOR can issue/verify an OTP only at ARRIVED and before verification. ADMIN can inspect and recover an eligible interrupted completion, but cannot start, arrive, verify or complete a trip. `routes/deliveries.js` returns HTTP 403 / `OPERATOR_REQUIRED` for administrator trip mutations; unknown or other-operator trips are protected separately. Missing controls on ADMIN are therefore an authorization boundary, not demonstrated broken OTP issuance.

The confirmed usability defect was absent visible guidance explaining this boundary. Before application edits, a regression assertion reproduced the absent Delivery verification heading in both desktop and mobile operator arrival flows. The ADMIN page now has a named Delivery verification region explaining the assigned-operator login, required states, ordinary citizen code and fictional demo OTP. The ARRIVED operator card now names its verification section. Existing button names, endpoints, state machine, credentials, hashes, expiry, attempt limits and quantity/accounting logic are unchanged. No ADMIN operator permission was added.

Tanker management was exercised using real forms/API/MongoDB: provision an operator, edit/link the demo tanker and explicitly confirm observations, then recommend/reject/approve/assign. Added coverage registers another UNAVAILABLE tanker, rejects available litres exceeding capacity without a Mongo write, saves bounded quantity, reloads and edits the name, and checks persisted capacity/water/status/name. The extra tanker does not manufacture an eligible allocation candidate. No independent tanker API defect was reproduced. The first added test used an incorrect accessible label; it was corrected to the existing **Identifier** field without changing application validation.

## Actual workflow evidence

Citizen browser cases register without automatic reports, explicitly select/capture/manual-enter location, submit optional sanitized photo and unknown supply/duration, retrieve Mongo-backed owned history/status after reload/login, and reject cross-citizen access. Lost-response retry retains submission identity and cannot duplicate the report or creation journal. Household size is citizen-provided; no neighborhood-population input exists.

Administrator cases review PENDING submitted evidence with required note and actor/time/correlation audit, reject other evidence, inspect derived clusters/map/score breakdowns, provision/link/edit fleet, review freshness/capacity, and separately recommend/reject/approve/assign. Tests reject unauthorized/out-of-order/concurrent actions. Submitted-evidence review is not identity, field inspection or physical shortage resolution. No artificial severity or fairness adjustment was introduced to force the illustrative hero numbers.

Operator cases authenticate into Your assignments, reject another operator's trip, inspect stored route/distance/estimated ETA, persist ASSIGNED → EN_ROUTE → ARRIVED, request the supported demo or designated-citizen handoff, reject wrong/expired/replayed codes, verify, enter bounded actual litres and complete. Completion records one accepted quantity and one debit, releases the reservation and preserves audit/status after restart. Network-loss recovery reads saved state rather than replaying actions. Controlled adapter and demo code tests are not proof of real SMS, live roads, GPS or household receipt.

The ordered acceptance journey uses one newly owned UUID database and actual browser/API/Mongo services. Its report→review→fresh simulated observation→recommendation→approval→assignment→trip→demo OTP→completion→advisory→forecast→analytics/audit sequence includes three backend process restarts. Citizen-portal code handoff is separately exercised by Phase 7 browser tests. Outcomes and exit are recorded below, separately from individual suite coverage.

## Forecast, source and citizen-alert results
